# Agent-state log v1 (R1) and `baken/log/1`

Status: **v1, implemented by `core/crates/core-log`.** Normative for every node that stores, verifies or replicates
agent logs. A change to a rule or an encoding is made here first, with its fixture.

Source: C1 §1 (foundations), §3 (R1) and §4 (`baken/log/1`), invariants L1-L12 and D1-D6, and the C1/C2
reconciliation (divergence inputs for C2's catalog node id). This document tightens C1 where implementation needed a
decision; section 12 lists every difference. Placement validity rules 2 and 3 (membership, quorum) are C6's and enter
through the `ClaimJudge` trait (section 6.2). Storage is `store/store-v1.md`.

Fixtures, beside this file (generated by `core/crates/core-log/tests/fixtures.rs`, checked in, compared on every test
run; regenerate with `BAKEN_REGEN_FIXTURES=1 cargo test -p core-log --test fixtures`):

- [`log-v1-vectors.json`](log-v1-vectors.json): test keys, hash contexts, signed entries, header and chain negative
  cases, payload BCBOR for every kind and negative payloads, epoch order.
- [`log-v1-scenarios.json`](log-v1-scenarios.json): chain and divergence scenarios with the expected canonical
  segment, placement, segment states and divergence inputs (including C2 catalog node ids).
- [`log-v1-wire.json`](log-v1-wire.json): one framed example of every `baken/log/1` message, invalid bodies, an
  oversize length prefix.
- BCBOR vectors are `../membership/bcbor-v1.json` (the profile is shared; `core_proto::bcbor`).

Rules marked **R-x** are normative. Test keys are Ed25519 seeds `k` repeated 32 times, named Nk.

## 1. Encodings

- **R-1 BCBOR.** Payloads and wire messages use the BCBOR profile v1 (C1 §1.1, implemented once in
  `core_proto::bcbor`): unsigned ints, byte and text strings, arrays, maps with strictly ascending uint keys,
  `true`/`false`/`null`; shortest forms; no floats, tags, negative ints or indefinite lengths; depth at most 16; no
  trailing bytes. Decoders reject anything else, so one value has one encoding. The CBOR encoding and decoding are the
  `minicbor` crate's; `core_proto::bcbor` adds only the profile checks (allowed types, shortest heads, key order,
  limits), so the bytes are standard CBOR any library reads.
- **R-2 Optional fields.** An optional map field is either absent or `null`; the two mean the same. Encoders omit it.
  Unknown keys are ignored by decoders and preserved by relays: a verifier hashes the payload bytes as received and
  never re-encodes them.
- **R-3 Epoch** is the array `[n uint, claimant bstr32]`. **Pos** is the map `{0: seq uint, 1: hash bstr32}`.
  Epochs order by `n`, then by the claimant's 32 bytes as an unsigned big-endian number (`epoch_order` vectors).

### 1.1 Entry header (168 bytes, big-endian)

| Offset | Length | Field | Rule |
|---|---|---|---|
| 0 | 4 | magic | `42 4B 4C 31` (`"BKL1"`) |
| 4 | 32 | `log_id` | `derive_key("agent log id", agent_id)` |
| 36 | 8 | `epoch.n` | 1 at genesis; 1 to `EPOCH_N_LIMIT` = 2^32 − 1 |
| 44 | 32 | `epoch.claimant` | node id; signs every entry of the segment |
| 76 | 8 | `seq` | agent-global height |
| 84 | 32 | `prev` | hash of the entry at `seq − 1` on this line; zero exactly when `seq == 0` |
| 116 | 2 | `kind` | section 3 |
| 118 | 2 | `flags` | bit 0 `compactable`; bits 1-15 are 0 |
| 120 | 8 | `ts_ms` | writer's wall clock, informational only |
| 128 | 8 | `payload_len` | at most `MAX_PAYLOAD` = 64 MiB |
| 136 | 32 | `payload_hash` | plain `blake3(payload)` |

A **signed entry** is `header ‖ Ed25519(claimant, entry_hash)`, 232 bytes. Signatures verify with the strict rules
(non-canonical `S`, small-order keys and small-order `R` are rejected).

Header decode errors (stable codes, `invalid_headers` vectors): `wrong_length`, `bad_magic`, `reserved_flags`,
`epoch_out_of_range` (n = 0 or above the limit), `payload_too_large`, `genesis_prev`, `bad_signature`.

### 1.2 Hashes

| Name | Definition |
|---|---|
| `entry_hash` | `derive_key("baken 2026-11-26 log entry v1", header)` |
| `log_id` | `derive_key("baken 2026-11-26 agent log id v1", utf8(agent_id))` |
| `divergence_id` | `derive_key("baken 2026-11-26 divergence id v1", log_id ‖ stranded_epoch(n BE u64 ‖ claimant) ‖ fork_seq BE u64)` |
| `log_digest` | `derive_key("baken 2026-11-26 log digest v1", …)`, section 9.4 |
| payload hash | plain `blake3(payload)` |
| manifest and `file_put` | SHA-256 of the file bytes |
| git object id | git's hash (`sha1` or `sha256`, as the repo uses) of `"<type> <len>\0" ‖ content` |
| C2 divergence node id | first 16 bytes of plain `blake3("baken.divergence.v1" ‖ agent_id ‖ 0x00 ‖ conversation_id ‖ 0x00 ‖ u64be(stranded.n) ‖ stranded.claimant)`, version nibble set to 8 and variant bits to `10` (RFC 9562 UUIDv8) |

The derive-key contexts live in `core_log::hashes`; `core_proto::crypto::derive_key` takes each crate's context.

## 2. Shape

- **R-10** An agent log is a set of segments, one per epoch. Only the epoch's claimant signs entries of its segment.
- **R-11** `seq` is agent-global: the first entry of a segment has `seq = parent.seq + 1`.
- **R-12** The first entry of every segment is an `epoch_open`; its `prev` is the fork point. Genesis is the
  `epoch_open` at seq 0, reason `genesis`, `n = 1`.
- **R-13** The canonical line runs from the canonical segment's head (section 6) back through `prev` to genesis.
  Every stored entry not on it is in a divergent tail.

## 3. Payload kinds

| Kind | Name | Payload (C1 §3.4) | Flags the holder writes |
|---|---|---|---|
| `0x0001` | `epoch_open` | `{0: agent_id (genesis only, required there), 1: reason (0 genesis, 1 move, 2 failover, 3 takeover, 4 takeover_forced, 5 rekey), 2: prior_epoch, 3: [vote envelope…], 4: store_format (required), 5: runtime_parity, 6: prior_head_seen Pos, 7: uncertain [Action…]}` | 0 |
| `0x0002` | `epoch_seal` | `{0: next_epoch Epoch or null (key required; null = release), 1: checkpoint Pos}` | 0 |
| `0x0003` | `checkpoint` | `{0: manifest [[path, sha256, len]…] strictly ascending by path, 1: refs [[repo, ref, oid]…] strictly ascending, 2: feed_heads [[conversation_id, feed_seq]…] strictly ascending, 3: store_format, 4: runtime_parity, 5: h1_violations [tstr…]}` | 0 |
| `0x0004` | `divergence` | keys 0-13 of C1 §3.4; `competing` strictly ascending; `stranded_holder` equals `losing_epoch.claimant` | 0 |
| `0x0100` | `file_put` | `{0: path, 1: sha256, 2: content, 3: exec}`; `sha256` must match `content` | compactable |
| `0x0101` | `file_append` | `{0: path, 1: offset (file length before), 2: bytes}` | 0 |
| `0x0102` | `file_delete` | `{0: path}` | 0 |
| `0x0200` | `git_objects` | `{0: repo, 1: algo ("sha1"/"sha256"), 2: [[oid, type 1-4, content]…]}`; every oid must match its content | 0 |
| `0x0201` | `git_ref` | `{0: repo, 1: ref, 2: old_oid or null, 3: new_oid or null}`, or `{0, 1, 4: symref}` for a symbolic ref | 0 |
| `0x0300` | `feed_append` | `{0: conversation_id, 1: feed_seq, 2: turn, 3: kind, 4: entry (feed v1 JSON, verbatim), 5: replaces_feed_seq}` | compactable |
| `0x0400` | `action_status` | `{0: idempotency_key, 1: tool_call_id, 2: conversation_id, 3: state (0 started, 1 finished, 2 failed, 3 acknowledged_uncertain)}` | 0 |

`Action` = `{0: idempotency_key, 1: tool_call_id, 2: conversation_id, 3: started_at Pos}`.

- **R-20 Paths** are relative, `/`-separated, at most 512 bytes, with no empty, `.` or `..` segment, no backslash and
  no NUL. A payload with a malformed path is invalid.
- **R-21 Allowlist (store_format 1)**: `agents/<name>.json`, `conversations/<key>/conversation.json`,
  `conversations/<key>/messages.jsonl`, `conversations/<key>/blobs/<name>`; memfs travels only as `git_objects` and
  `git_ref`. An entry naming another path is stored and relayed (chain integrity), never materialized, and alarmed.
- **R-22 Unknown kinds** are stored and relayed verbatim. Kinds from `0x8000` are ignorable by a materializer; an
  unknown kind below `0x8000` on the canonical line makes the log unmaterializable on this node
  (`store_format_unsupported`).
- **R-23** A payload of a known kind that fails to decode (non-canonical BCBOR, a missing required key, a broken
  rule) makes its entry invalid: it is refused with `bad_encoding`. Payload decode errors have stable codes
  (`invalid_payloads` vectors): `bcbor_<profile code>`, `missing_key`, `wrong_type`, `invalid`.

## 4. Entry validity (every replica, independent of placement)

An entry is refused, and not stored, unless:

- **V1** its header decodes and its signature verifies (section 1.1);
- **V2** an inline payload matches `payload_len` and `payload_hash` (`PayloadMismatch`, wire `bad_encoding`), and
  decodes (R-23);
- **V3** at seq 0: it is an `epoch_open` with reason `genesis`, `n = 1`, and `log_id = derive_key("agent log id",
  payload.agent_id)`; at seq > 0 no `epoch_open` has reason `genesis`;
- **V4** at seq > 0: the stored entry with hash `prev` is of the same log at `seq − 1`; and an `epoch_open` has its
  `prev` in another epoch while every other kind has it in the same epoch.

Chain failures are `chain_mismatch` (`invalid_chain` vectors). An entry whose `prev` is not stored yet is **pending**:
the receiver buffers it keyed by `prev` (at most `PENDING_PER_LOG` = 4,096 per log; on overflow the buffer is dropped
and the log re-wanted) and stores it when its parent arrives. Inserts are idempotent (keyed by `entry_hash`); a known
entry whose payload was missing takes a later inline payload.

## 5. Segments

- **R-30** One segment row per `(log, epoch)` (store v1). If a claimant opened one epoch twice (two fork points), the
  open with the lower `entry_hash` is the segment's start whatever the arrival order; the other open and its entries
  are off the segment (and, when they hang off the canonical line, a divergence).
- **R-31 Head.** From the open, at each seq the child in the same epoch with the lowest `entry_hash` stays in the
  segment (the equivocation rule); the head is the last entry reached.
- **R-32 complete_seq** is the highest seq from the open along the head chain such that every payload up to it is
  stored, or pruned and compactable.

## 6. Evaluation: validity, ratification, canonical segment, placement

Evaluation is a pure function of the stored entries and the judge, so replicas with the same entries and membership
reach the same result in any delivery order (scenario and property tests).

### 6.1 Structure (claim rule 1, checked by the log)

A segment is **line-ok** when its open is genesis (`seq 0`, `n = 1`) or its parent's epoch `p` satisfies
`p.n < n ≤ p.n + EPOCH_N_MAX_STEP` (2^20), and its parent's segment is line-ok. A segment that is not line-ok is
`invalid`.

### 6.2 The judge (claim rules 2 and 3)

`ClaimJudge::claim_valid(ClaimContext)` sees the open, its decoded payload, the parent entry and the parent's payload.
It must be a pure function of that context and the judge's membership state. `core-placement` implements it over a
membership view (active claimant with `node.execute`; `node.takeover` for failover and takeover; certificates;
`admin.full` for forced takeover; `rotated` for rekey). `StructuralJudge`, used by replicas that do not evaluate
membership and by these fixtures, checks only: genesis only at seq 0 with `n = 1`; a move only when the parent is an
`epoch_seal` whose `next_epoch` is the open's epoch; every other reason accepted.

### 6.3 Ratification and the canonical segment

- **R-40** A segment is **valid** when it is line-ok and either its open's payload is held and the judge accepts it,
  or it is ratified: some valid segment's open has its parent in it. Segments are judged in descending epoch order,
  so ratification is transitive.
- **R-41** The canonical segment is the valid segment with the highest epoch. Its open always has its payload (the
  judge needs it).
- **R-42 Placement state**: `superseded_unknown` when `max_n_seen` (every stored entry, any classification) exceeds the
  canonical `n`; else `sealed_to(next)` or `placeless` when the canonical head is an `epoch_seal`; else `active`.
- **R-43 Segment states**: the canonical segment is `open` (or `sealed` when its head is a seal); a segment holding a
  canonical-line entry is `canonical_ancestor`; otherwise `invalid` (not line-ok), `quarantined` (open payload not
  held, not ratified), or `divergent`.
- **R-44 Applying it** (in the transaction that stored the entries; C1 F1-F5): a higher canonical epoch is adopted
  with `adopt_epoch` (its open, segment and placement together, F2); a lower one through `fall_back_placement` (its
  tip lost validity, P8); a state change through `set_placement_state`. Segment rows are rewritten with their states.
  Nothing stored is ever deleted or rewritten (F5, L3).
- An entry that only extends the active canonical segment's head, with nothing else at its seq and no higher `n`
  known, needs no re-evaluation (the live-tail fast path).

## 7. Holder

- **R-50 Gate (F4).** A node appends only when it is the canonical epoch's claimant, the placement is `active` and
  `max_n_seen` equals the epoch's `n`. Otherwise `NotHolder` (wire `forbidden`).
- **R-51 Append** takes `seq = head + 1`, `prev = head`, the kind's flags (section 3), signs and stores entry, payload
  and segment head in one transaction. An `epoch_seal` also moves the placement to `sealed_to` / `placeless`; after it
  the claimant never writes in that epoch again.
- **R-52 Claim.** `n = max(max_n_seen, parent.n, s) + 1`, where `s` is the sealed-to `n` when the parent is an
  `epoch_seal` naming a next epoch and the claim is not that move (else 0), so a late open by the seal's target is a
  divergent tail, never a tie on `n`; `prev` = the named fork point, at most `EPOCH_N_MAX_STEP` above
  the parent. The judge is asked first; a refused claim is not stored. A valid claim becomes canonical in its
  transaction, and the old line past the fork point becomes a divergent tail.
- **R-53** The holder records a divergence with `record_divergence`: the `divergence` entry (section 8.4) and the
  record's `recorded_entry`.

## 8. Divergence

### 8.1 Evidence and tails

An off-line entry X at seq `q > 0` whose `prev` is on the canonical line, where the line also has an entry C at `q`,
is the **root** of a divergence (two valid entries at one position). Its **tail** is X and every stored off-line
entry descending from it (across segments). Tails are stored for ever, relayed, and never materialized (L10).
Off-line trees with no fork point (a second genesis) are divergent but name no divergence.

### 8.2 Canonical divergence inputs (for C2)

Every replica derives, from the stored entries alone:

| Input | Value |
|---|---|
| `agent_id` | from the genesis payload |
| `fork` | the line entry at `q − 1`: `(fork_epoch, fork.seq, fork.hash)` |
| `competing` | `[X.hash, C.hash]` sorted ascending bytewise |
| `stranded_epoch` | X's epoch (C2's stranded epoch; `stranded_holder` is its claimant) |
| `winning_epoch` | C's epoch |
| `equivocation` | `stranded_epoch == winning_epoch` (then the fork epoch is the same too) |

`divergence_id` = section 1.2. Two roots with the same stranded epoch and fork seq are one divergence: the root with
the lower hash names it, and the tails merge. The tail head is the tail's highest seq, ties to the lowest hash.

From the inputs: the C2 catalog node id per conversation (section 1.2); the branch conversation id
`"local-conv-" + <that UUID, lowercase hyphenated>`; memfs branch names
`refs/heads/divergence/<stranded.n>-<first 8 hex of stranded.claimant>/<leaf>`. Either side of a partition can write
the catalog node from these before the holder's `divergence` entry exists; the writes are equal (D5). Scenario
vectors list the inputs and node ids for each divergence case.

### 8.3 Records

The store's divergence records are an append-only history of what the replica observed: a later record with the same
id supersedes (the tail may grow), and a record made against an intermediate canonical line (entries arriving out of
order) is kept. The current divergence set is evaluation's output (section 6), identical on every replica; the holder
acts on that, not on the record history.

### 8.4 The holder's `divergence` entry

Built from the inputs plus `core-projection`'s diff of the two lines (C1 §6.3: conversations with their last common
message and owning agent, memfs branches, uncertain actions, `from_revoked`): keys 0-13 of section 3, with
`catalog_node_id` and `branch_conversation_id` derived as above. Written when the losing claimant reports `fenced`,
or 10 minutes after the tail last grew, and again with the same id if the tail grows (C1 §3.8; timing is C6/C10's).

## 9. `baken/log/1`

### 9.1 Framing

One bidirectional stream per connection. A frame is a `u32 BE` length, then a BCBOR map whose key 0 is the message
type; at most `MAX_FRAME` = 1 MiB (a larger prefix is `too_large` and ends the stream). The version is in the ALPN.
This is the default framing of `tokio_util`'s `LengthDelimitedCodec` (a 4-byte big-endian length that does not
count itself), which the Rust core uses for it.

### 9.2 Messages

| Type | Name | Fields |
|---|---|---|
| 1 | `hello` | `{1: version (1), 2: node_id, 3: constellation_id, 4: member_heads sorted set, 5: log_digest, 6: mode (0 live, 1 heads_only), 7: store_format}` |
| 2 | `have` | `{1: [AgentHave…] (at most 256), 2: last bool}` |
| 3 | `want` | `{1: log_id, 2: epoch, 3: after Pos or null, 4: live, 5: payloads}` |
| 4 | `entries` | `{1: log_id, 2: [[signed entry bstr232, payload]…]}`; payload is a bstr (inline, at most 192 KiB), `0` (by hash over `baken/blob/1`) or `1` (pruned) |
| 5 | `ack` | `{1: log_id, 2: epoch, 3: Pos}` |
| 6 | `head` | `{1: log_id, 2: epoch, 3: Pos}` |
| 7 | `ping` | `{1: nonce, 2: [[node_id, ms_since_heard]…]}` |
| 8 | `resync` | `{1: log_id, 2: reason}` |
| 9 | `error` | `{1: code, 2: message, 3: log_id (optional)}` |

`AgentHave` = `{0: log_id, 1: agent_id, 2: hwm Epoch, 3: max_n_seen, 4: tip Pos, 5: complete_seq, 6: [SegSummary…]}`;
keys 1, 2, 4 and 5 may be null when unknown. `SegSummary` = `{0: epoch, 1: start_seq, 2: parent_hash (null for the
genesis segment), 3: head Pos, 4: state, 5: entries uint, 6: set_xor bstr32}` with the store v1 state codes (0 open,
1 sealed, 2 canonical_ancestor, 3 divergent, 4 invalid, 5 quarantined). `entries` is the number of stored entries of
the segment (every branch) and `set_xor` the XOR of their entry hashes: together they tell two replicas whether they
hold the same set even when branches off the head differ.

Error codes: `constellation_mismatch`, `not_member`, `forbidden`, `bad_signature`, `bad_encoding`, `chain_mismatch`,
`unknown_segment`, `too_large`, `rate_limited`, `store_format_unsupported`. Wire decode errors in the fixtures:
`unknown_type`, `too_large`, and the payload shape codes of R-23.

### 9.3 Session

1. Both sides send `hello`. A different constellation is answered with `error constellation_mismatch` and the
   stream closes. Different membership heads raise a membership sync (`baken/member/1`); entries received meanwhile
   are stored and evaluated with the judge's current state.
2. Equal digests: each side sends one live `want` per log it holds (`after` = its canonical head) and skips 3-4.
3. Otherwise each side sends `have` for every log (`last` on the final frame).
4. On the peer's last `have`, a side wants, per log and segment: an unknown segment whole (`after` null); a known
   segment whose `(entries, set_xor)` differ from its own: from its own head when the peer's summary is a pure
   extension of its chain (peer head not held, peer head seq above its own, and the entry-count difference equal to
   the seq difference), else whole. Once it holds
   the peer's announced head it compares the sets again and, if they still differ, wants the whole segment (once per
   session). An entry that goes pending in a session (its parent is on a branch this side never asked for) makes it
   want the whole epoch of that entry, or, for an `epoch_open`, every segment the peer announced, once per session.
   Wants go unknown segments first (fencing information first), then gaps, each in epoch order. The last
   want of each log is `live`; a log with no want gets a live want from its canonical head.
5. The responder streams `entries` of the wanted segment from `after` (all entries of that epoch at seq above
   `after.seq`, every branch; with `after` null, every entry of that epoch it holds, including a second open), at most `MAX_BATCH_BYTES` (768 KiB) and 512 entries per frame. A live want subscribes the peer to the
   log: every entry stored later (by this node or relayed from any session) is pushed, whatever its segment, a new
   `epoch_open` ahead of queued entries. With a live want the responder also sends a `head` for each of the log's
   other segments; a receiver wants any head it does not hold (unless it already asked for that far). When a node
   stores entries of a log a peer has not subscribed to (a log new to the peer), it announces that log's segment
   heads to the peer once; a receiver's want for a log it has no live subscription to is live.
6. The receiver verifies and stores each entry (section 4), evaluates the log once per frame when needed, commits,
   and then acks: one `ack` per segment touched by the frame, naming the highest position of that segment it took
   from the frame (stored, duplicate or buffered). It reports newly stored entries to its node, which pushes them to
   the node's other live subscribers: every replica relays.
7. `heads_only` peers get `head` notices instead of pushed entries and want when they choose.

### 9.4 Digest

`log_digest = derive_key("log digest", concat over logs ascending by log_id of (log_id ‖ hwm.n BE u64 ‖ hwm.claimant
‖ tip.seq BE u64 ‖ tip.hash ‖ max_n_seen BE u64 ‖ divergent_segment_count BE u32 ‖ concat over segments ascending by
epoch of (epoch.n BE u64 ‖ epoch.claimant ‖ entries BE u64 ‖ set_xor)))`, from the placement row (hwm), the canonical
segment row (tip) and the segment rows; a log without placement contributes zeros for hwm and tip. Equal digests mean
equal entry sets, so the catch-up can be skipped.

### 9.5 Backpressure (credit by ack)

- A sender keeps at most `UNACKED_PER_LOG` (512 KiB) unacked per log and `UNACKED_PER_CONN` (4 MiB) per connection.
  A frame never exceeds the remaining credit (one entry may, when nothing is unacked). An `ack` for `(log, epoch,
  Pos)` releases every sent entry of that segment at or below `Pos.seq`.
- Catch-up waits for credit. A live tail over budget for `BACKPRESSURE_RESYNC_MS` (5 s) is dropped: the sender
  unsubscribes the log and sends `resync {reason: "backpressure"}`; the receiver re-wants every segment of the log
  from its stored heads, the last one live.
- `ping` after `PING_INTERVAL` (15 s) without sending.

### 9.6 Resumption

There is no session state to resume: every session starts at step 1 and every `want` names the receiver's durable
stored head. Duplicates are no-ops, so a reconnect yields no gap and no duplicate (L5). Acks a sender received live in
memory for the session only.

### 9.7 Driver and link

The async driver (`core_log::driver::run_session`) runs one session over two halves of a byte stream (tokio's
`AsyncRead` and `AsyncWrite`, framed by `tokio_util`; no tokio runtime needed) with a `Clock`; it handles each frame in
one store transaction and sends replies after the commit. Iroh's QUIC streams implement those traits directly. A node's `Hub` fans
stored-entry notices out to its sessions; the holder publishes its own appends there after committing them.

## 10. Retention and pruning

- **R-60** Headers are kept for ever, canonical and divergent.
- **R-61** Only compactable payloads on the canonical line are pruned, each replica on its own; divergent tails keep
  every payload.
  - `file_put`: when a later `file_put` of the same path exists, both at or below the latest canonical `checkpoint`,
    with no `file_append` or `file_delete` of that path, and no `file_put`/`file_append` whose payload is missing,
    between them. A materializer that skips the pruned entry folds the same bytes (L11).
  - `feed_append`: one named by a later `replaces_feed_seq`; then, per conversation, the oldest entries of finished
    turns (a `turn_closed` entry exists for the turn) until at most 1,000 entries and 4 MiB remain. A running turn is
    never pruned.
- **R-62** A pruned payload is served as `1`; a receiver accepts `1` only for a compactable entry (it marks it pruned,
  so `complete_seq` passes it), and keeps any other entry's payload missing.
- **R-63** Verification (`verify_log`) re-checks every header's signature, chain link and held payload hash; pruned
  payloads of compactable entries never break it.

## 11. Invariants covered here

| Invariant | Where |
|---|---|
| L1 one signer per segment | V1 with the claimant as signer; `SignedEntry::sign` refuses another key |
| L2 contiguous canonical line | evaluation; property `replicas_converge_whatever_the_order` |
| L3 headers only grow | store S-10; properties (every valid header stored), pruning keeps headers |
| L4 convergence | properties `replicas_converge_whatever_the_order`, `sessions_converge`; scenario replay in three orders |
| L5 no gap, no duplicate | idempotent insert, stateless resume; `sessions_converge`, driver test |
| L6 complete_seq bound | R-32; `sessions_converge` |
| L9 divergence recorded with one id | section 8; properties check every competing entry is in a tail, same ids everywhere |
| L10 tails never materialized | `canonical_line` excludes tails; holder and property checks |
| L11 pruning keeps the manifest | R-61; `pruning_never_breaks_verification`, holder pruning test |
| D1 both continuations kept | failover holder test, scenarios |
| D5 identical divergence inputs | section 8.2; scenarios (three orders) and properties |

## 12. Differences from C1

- `want.after` may be null: every entry of that epoch the responder holds. A segment's parent cannot name everything
  (the genesis segment has none, and a claimant's second open of an epoch may sit at another seq).
- `ack` names the highest position of the segment the receiver took from the frame, not `complete_seq`: credit must
  not stall while a large payload is fetched by hash. `complete_seq` travels in `have`.
- `have` fields `agent_id`, `hwm`, `tip`, `complete_seq` may be null, and `SegSummary.parent_hash` is null for the
  genesis segment.
- A live `want` also triggers `head` hints for the log's other segments, so a receiver that re-wants after `resync`
  learns of segments it missed; a node announces a log new to a peer with `head` notices.
- `SegSummary` adds `entries` and `set_xor`, and the digest covers them: comparing heads alone misses branches below
  a segment's head (equivocation, a claimant's second open), and a digest without them could skip a needed catch-up.
- The `file_put` pruning rule adds "no `file_append`/`file_delete` of the path between": the header does not carry the
  path, so a materializer cannot tell which file a pruned put wrote.
- R-30 (two opens of one epoch) and the stranded/winning epoch definitions (section 8.2) fix choices C1 left open.
- Divergence records are history (section 8.3); C1 implied they converge.
- Wire messages live in `core-log` (`core_log::wire`), not `core-proto`, since only this crate speaks the protocol;
  they can move when another crate needs them.
