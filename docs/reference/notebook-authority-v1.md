# Host notebook grants v1

This contract specifies the host-owned grant store for notebook references and editing. It is independent of notebook content, the local document index, pairing, agent IDs and canvas permissions. The principal is the authenticated Iroh remote endpoint ID obtained from the connection, never a request parameter. Pairing or transport authentication alone creates no notebook grant.

The UTF-8 JSON store has exactly `version` (integer 1) and `grants` (array). Each entry has exactly `principal`, `documentId`, `mayRead`, `mayEdit`, and `mayReference`. The principal and document ID are nonempty exact strings; duplicate pairs or object fields, unknown fields, missing fields, wrong types and unsupported versions are configuration errors. Capabilities default to nothing: all three booleans must be present. A missing store denies; malformed or unreadable stores deny and report an unavailable/configuration diagnostic. The example at `android-compose/sharedLogic/src/jvmTest/resources/notebook-authority/grants-v1.json` is the format fixture, not a source of default grants.

Trusted host administration provisions and revokes entries using the same lock and atomic replacement protocol as the serving process. The file and lock directory must be protected against untrusted writes. Direct edits while a host is serving are not part of the protocol. Each operation reloads the store under a shared exclusive lock, held through the protected mutation or read; provisioning and revocation take that same lock. A revocation that completes before a mutation starts prevents it; one concurrent with a mutation waits for that mutation to finish, or wins the lock and prevents it. A timed-out or cancelled queued mutation withdraws its callback before the lock is released. If its in-memory transaction has already started, the callback fence waits for it to finish before releasing the lock; asynchronous persistence of that accepted history may still complete later. This is not a distributed lock for Automerge peer writes or a guarantee against an administrator bypassing the protocol.

On Windows, mount records proceed with forced contents and atomic replacement but cannot confirm the directory entry: after a power cut the newest binding may be missing and is simply set again. Notebook grants instead refuse provisioning and revocation before taking a lock or touching files, because a lost revoke could restore access. `serve-iroh --notebook-grants-file` and `notebook-grant` refuse with a usage error; use a host that can confirm directory durability for notebook sharing. Existing grant files remain readable, and an absent file denies access.

Grant administration requires a host filesystem that supports atomic replacement and directory synchronization. Provision/revoke check directory synchronization before replacing the file and confirm it again afterward. Unsupported synchronization and I/O failures are explicit errors. A failure after replacement may leave the new grant record visible, but does not confirm crash durability; administration must reload and retry rather than acknowledge success. File synchronization alone does not confirm a renamed directory entry ([Linux fsync documentation](https://man7.org/linux/man-pages/man2/fsync.2.html)).

Every reference lookup, including nested lookups, requires both read and reference on the exact principal/document pair before storage is consulted. An editor open requires fresh read and edit grants, because its response includes notebook content; every save and flush checks both again under the mutation lock because their results can include snapshots. Denial does not erase an editor draft or acknowledge an unflushed write. Storage absence, access denial, and configuration or storage failure remain distinguishable. Cancellation and the existing note session's indeterminate-write and durability semantics remain in effect.

The pinned Automerge 0.0.9 RepoConfig provides only an announce policy, with no authenticated per-document incoming-mutation hook. Grant-protected stores must refuse raw repository exposure for both accept and dial. An already exposed repository must refuse grant activation, even if its links appear closed: retained native handles cannot be reauthorized. The wrapper must reject --notebook-grants-file combined with --notebook-dir / --notebook-peer-ids before loading storage or binding an endpoint, regardless of missing, valid or corrupt grant data. Use --notebook-authority-dir plus --notebook-grants-file without sync options. This is an explicit incompatible configuration error, not a silent change to existing sync-only deployments.

This prerequisite is RPC-only grant enforcement, not multi-peer grant-aware synchronization. To transition a sync deployment, the host administrator must stop its raw-sync process and all other raw access to that directory, then start the RPC-only configuration; clients require the authenticated notebook RPC route. Revocation applies to subsequent RPC operations, not copies already received by a peer. The existing opt-in Samod repository sync retains its legacy trust boundary when grants are not configured: its configured peer allowlist attaches the peer to the repository and its current announce policy excludes retired documents only. This contract does not establish per-document enforcement on that sync path. A peer with direct repository access may already hold document data and can exchange repository changes independently of the operations described here.

## Authenticated host operations

The wrapper's scoped admin RPC binding derives the principal from the current authenticated Iroh connection. Each request contains `document_id` (the exact lowercase 32-character notebook ID); any `agent_id` or principal-like field is data and cannot select a grant. `notebook.reference.resolve` returns `status` of `found`, `denied`, `missing`, or `unavailable`, with `document` on `found`. `notebook.note.open` performs a new edit check and returns `found` plus `snapshot`, `denied`, `missing`, or `unavailable`. `notebook.note.save` additionally requires string `expected` and `replacement`; `notebook.note.flush` requires the prior `snapshot`. Save and flush return `saved`, `conflict`, `pending_durability`, `denied`, or `unavailable`, carrying the corresponding existing note result fields. Unknown methods and malformed required parameters are errors. Extra identity-like fields never select a principal.

The wrapper can open an existing notebook directory for these operations with `--notebook-authority-dir` and `--notebook-grants-file`; its Iroh secret-key file supplies the stable host peer identity. Do not combine the grant file with `--notebook-dir` or `--notebook-peer-ids`; startup rejects that unsafe combination. Existing sync-only deployments require an explicit coordinated transition to RPC-only operation before using grants. The grant file must be outside notebook storage and its existing parent directory must be protected by the host administrator. The host-local `notebook-grant` command takes `--file`, `--principal`, and `--document`, plus explicit `--read`, `--edit`, and `--reference` flags; `--revoke` removes that pair. Both commands use the same file-lock protocol. Anonymous or paired peers still require an explicit document grant.
